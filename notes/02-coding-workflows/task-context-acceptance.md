# 从任务定义到验收：让一次 AI 修改可以被检查

> 用途：把“帮我改好”变成范围明确、上下文够用、结果可核验的小任务。先建立协作闭环，再补工具细节。
>
> 阅读位置：按当前任务选读；需要区分角色与证据时回看 [Foundations：先看懂一次 AI Coding 任务](../01-foundations/ai-coding-overview.md)。
>
> 前置：能阅读简单函数、条件分支和基本测试；不需要 Python、模型 API 或 Agent 框架。
>
> 配套实践：[修复 C++ 端口解析函数](../../labs/01-task-context-acceptance/README.md)。也可用已有真实项目的小修复替代，验收目标相同。

## 1. 快速复习

| 要回答的问题 | 最小产物 | 常见遗漏 |
| --- | --- | --- |
| 要改变什么？ | 目标行为和不改变的行为 | 只有“优化”“修复”一类动词 |
| 依据是什么？ | 接口约定、相关实现、错误或测试 | 只给报错截图，没有输入和运行方式 |
| 可以动哪里？ | 允许修改的文件、接口和依赖边界 | 默认可以重构整个模块 |
| 怎样知道完成？ | 行为检查、运行结果和差异审查 | 把“AI 说完成”当作证据 |
| 我是否理解？ | 解释关键逻辑，处理小变式或故障 | 用系统测试通过替代个人验收 |

任务定义、上下文与验收共同约束一次修改：任务定义要达成的行为，上下文提供判断所需的依据，验收把完成条件变成可检查的证据。

## 2. 基础关系回顾

模型、客户端、工具、Agent 及上下文的基本关系，统一见 [Foundations 导读](../01-foundations/ai-coding-overview.md)。角色定义维护在导读中，本篇集中练习工作流。

这里继续使用同一判断原则：解释文字、实际工具执行与结果正确需要不同证据；模型或客户端的不可见信息标记未知，不猜测内部行为。

## 3. 把任务写成行为约定

“让配置解析更健壮”没有说明合法输入、失败行为和允许修改范围。即使生成的代码能运行，双方也可能对“完成”有不同理解。

一个可执行的小任务至少明确：

1. **目标**：针对哪个问题，期望出现什么行为。
2. **依据**：接口说明、相关实现、输入样例、失败现象。
3. **边界**：允许修改哪些文件，哪些接口或已有行为必须保留。
4. **验收**：怎样检查目标行为、边界行为和修改范围。

OpenAI 的[最佳实践](https://learn.chatgpt.com/guides/best-practices)也建议在任务中提供目标、相关上下文、约束和完成条件。本节把这四项落到一个小修复中；它们是减少猜测的检查项，不是保证成功的固定提示词。

### 一个不涉及本实验答案的例子

给已有程序增加 `--version`：先说明输出格式、退出码、是否允许与其他参数组合，以及已有参数行为应如何保留。随后提供参数处理入口和测试命令，限定修改范围，用输出断言与旧测试检查结果。

如果“是否允许组合参数”尚未决定，就把它列为待澄清项。不要让 AI 随机补一个约定，再把实现当成原始需求。

### 验收必须约束行为

| 模糊表述 | 更可检查的表述 |
| --- | --- |
| 代码足够健壮 | 指定合法输入、非法输入、边界和失败后的状态 |
| 测试全部通过 | 给出运行命令，保留旧用例，并补覆盖本次风险的断言 |
| 修改尽量少 | 列出允许修改文件，解释新增逻辑，审查有无无关差异 |
| 解释清楚 | 能结合具体分支说明输入如何变成结果，以及失败时什么状态应保留 |

## 4. 必要上下文：选择判断依据

上下文是这次任务中系统可用的信息。项目里的文件不一定全部进入模型输入；路径可访问也不等于已经读取。这里关注可以核对的事实：提供了哪些材料、工具实际读取了什么、还缺少什么。

优先补齐能回答这些问题的材料：

- 接口约定是什么，谁调用它？
- 当前实现在哪，问题如何复现？
- 什么不能改变，相关测试怎样运行？
- 文档与代码是否描述同一版本，是否存在冲突？

通常先定位文件和符号，再读取相关实现、调用点与测试；发现缺口后继续补充。既不要求把整个仓库塞进任务，也不把“越少越好”当作目标。

在配套实验中，由学习者先判断接口说明、实现和已有测试各自能提供什么信息，再决定给 AI 哪些入口。正文不预填个人选择与预测。

出现冲突时，先区分信息性质：现行要求、历史说明、实现现状和测试期望可能不一致。实现和测试都可能有错；应回到明确的任务约定判断，必要时澄清，不能简单以文件更长或测试能跑为准。

## 5. 一个可检查的执行闭环

### 5.1 修改前：留下基线

基线是修改前的状态，包括相关文件版本、复现输入和原测试结果。先运行已有检查，区分已存在的问题与本次引入的问题。

如果编译失败，先处理编译命令或环境；此时还不能判断功能测试是否通过。若旧实现本来就应在某些用例失败，保留失败证据，不通过删除用例把它变成成功。

### 5.2 修改中：保持约定可追踪

允许 AI 帮助分析和实现，但要求改动对应明确需求。新增依赖、改变接口、移动项目或大范围重构若超出任务边界，应先说明原因并取得相应授权。

不要一开始预设某种提示一定更好。如需比较提示或上下文选择，应从同一代码基线开始，尽量只改变一个因素，并记录每次实际尝试。单次成功只能证明本次任务的观察结果。

### 5.3 修改后：先看证据，再听解释

依次检查：

1. **差异**：实际改了哪些文件，是否越界，旧测试是否被削弱。
2. **行为**：正常输入、必要边界和失败场景是否符合约定。
3. **执行证据**：命令是否实际运行，退出码和输出是什么，对应哪个版本。
4. **代码解释**：关键判断、数据流和失败路径能否说清楚。
5. **局限**：哪些要求尚无证据，哪些环境没有验证。

如果一个无条件返回成功的错误实现也能通过测试，测试就没有覆盖它声称要验证的失败行为。增加测试应针对风险与遗漏，不按用例数量追求覆盖感。

OpenAI 的[Skills 评测文章](https://developers.openai.com/blog/eval-skills)强调先定义成功，再记录运行并做针对性检查。本节借用这一评估思路，不要求实现 Skills 或评分框架。

## 6. 系统产出与个人掌握分别验收

| 系统产出 | 个人掌握 |
| --- | --- |
| 修改符合接口与范围约定 | 能解释目标、输入与范围为何这样定义 |
| 测试确实执行，结果可定位 | 能说明测试在检查什么、还遗漏什么 |
| 实际产物与说明一致 | 能解释关键分支、变量变化与失败状态 |
| 已知限制如实记录 | 能处理一个小约束变化，或根据故障证据组织定位 |

个人验收允许查阅资料和使用 AI。关键是本人能组织问题、判断依据、核对结论并应对变化，不能仅把 AI 给出的解释重新粘贴一遍。

个人预测、所需帮助、解释表现和掌握状态保存在本地计划。公开笔记只收录经过核实、适合复用的结论与脱敏证据。

## 7. 开始实践与迁移

优先选择合适的真实项目任务；没有合适任务时使用[端口解析实验](../../labs/01-task-context-acceptance/README.md)。按任务说明记录自己的上下文选择和预测，再让 AI 参与修复。只完成这一个闭环，不同时补完整模型原理或 Agent 课程。

如果已有真实项目小任务，满足以下条件就可以替代：

- 目标与修改边界明确，源码和测试保留在原仓库。
- 有修改前基线、修改后差异和有效测试证据。
- 能解释关键代码，并有小变式或故障处理证据；缺少哪项，只补哪项。
- 本仓库记录协作方法和定位到提交、文件、测试或复盘的链接。

## 8. 失败边界与待实践问题

- 约定错误时，代码完全符合约定也可能解决不了真实问题；先检查任务定义。
- 有限测试通过不能证明所有输入正确，解释流畅也不能证明个人已掌握。
- 同一系统同时生成实现与测试时，可能在两处复用同一个误解；仍需从约定独立检查用例与预期。
- 工具记录只支持其可观察范围，不据此推断不可见的模型内部机制。
- 本节没有证明某种提示词、客户端或上下文长度普遍更可靠。

实践后再回答：哪些信息真正减少了猜测？哪条测试最能区分错误实现？本人在哪一步依赖了帮助？换一个输入或约定后，原结论还成立吗？本页不提前填写结果。
