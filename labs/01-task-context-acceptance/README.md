# 实验 01：定义任务、选择上下文、核验一次 C++ 修复

这是可选的独立练习。需要时回看 [Foundations 导读](../../notes/01-foundations/ai-coding-overview.md)与[任务工作流](../../notes/02-coding-workflows/task-context-acceptance.md)；已有真实项目任务覆盖同样目标时无需重复完成。选择本实验后，仍按其契约、允许范围和验收条件开展。本实验使用普通字符串函数练习 AI 协作，不建立网络连接，不需要 API 密钥，也不要求实现 Agent。

## 1. 任务与材料

修复 `parse_port`，使它符合[头文件中的接口约定](include/port.h)，并补充已有测试未覆盖的输入类别。端口范围与文本规则是本实验的明确业务约定，不假设所有网络程序都采用相同规则。

| 材料 | 用途 |
| --- | --- |
| [port.h](include/port.h) | 接口、合法输入、失败行为及范围约定 |
| [port.cpp](src/port.cpp) | 故意带有缺陷的起始实现，保留供实际练习 |
| [port_test.cpp](tests/port_test.cpp) | 可直接运行的起始测试，覆盖部分行为，尚不完整 |

允许修改本实验的 `src/port.cpp`、`tests/port_test.cpp`。头文件和任务约定保持不变；构建产物只写本实验的 `work/`。不改其他课程文件、不安装依赖、不提交或推送。需要扩大范围时先说明原因。

这段范围只适用于本次练习，不代表获得其他仓库或整个计算机的访问授权。正文示例中的“允许”也不是软件权限设置，需要与当前工具权限共同满足。

## 2. 先写自己的判断

运行前，在本地计划中记录，不把这些答案写进公开起始材料：

1. 准备给 AI 哪些文件或入口？各自能提供什么依据？
2. 现有测试中，预计哪些行为可能失败，为什么？
3. 哪些要求尚没有测试证据？准备补哪类输入？
4. 怎样证明修复没有修改接口、削弱旧测试或改变失败后的输出？

允许查 C++ 文档，先留下自己的判断再使用 AI 解释。不会某个库函数时，标记未知，不伪造预测。

## 3. 环境与运行

需要能使用 C++11 或更新标准的编译器。以下命令以已有的 `g++` 为例；若命令不可用，先记录环境阻塞，不把编译器缺失记成功能失败，也不要求为本实验迁移系统。

### Windows / PowerShell

从本实验目录执行。先检查编译成功，再运行，避免误执行旧二进制。

```powershell
g++ --version
New-Item -ItemType Directory -Force work | Out-Null
g++ -std=c++11 -Wall -Wextra -Wpedantic -I include src/port.cpp tests/port_test.cpp -o work/port_test.exe
if ($LASTEXITCODE -ne 0) { throw "编译失败，停止运行" }
& .\work\port_test.exe
$testExitCode = $LASTEXITCODE
Write-Output "test exit code: $testExitCode"
```

### Linux / Bash

只有实际使用 Linux 时才需要这一组命令：

```bash
g++ --version
mkdir -p work
g++ -std=c++11 -Wall -Wextra -Wpedantic -I include src/port.cpp tests/port_test.cpp -o work/port_test && ./work/port_test
test_exit_code=$?
printf 'build or test exit code: %s\n' "$test_exit_code"
```

编译器返回非零表示构建失败；编译成功后，测试程序返回 0 表示当前用例全部通过，返回 1 表示至少一项失败。测试会输出每个用例及汇总。起始实现预期出现功能失败，这是保留的教学基线；先预测，再自行观察实际用例结果。

## 4. 让 AI 参与一次修复

先用自己的话写任务，包括目标、所选上下文、允许范围、完成条件和交付证据。正文不提供已填好的本实验提示词，避免把任务定义变成复制练习。

本次可以让 AI 分析、修改和运行测试；本人负责审查其依据与结果。没有实际执行工具时，AI 应把命令标成建议，不能声称已运行。若使用同一学习对话，让它说明已看到的材料，不宣称做了“完全相同起点”的提示对比实验。

执行后：

- 对照头文件逐条检查修改，不以“看起来更复杂”判断质量。
- 保留起始测试，增加针对未覆盖要求的断言；不只判断“没有抛异常”。
- 重新编译并运行，记录命令、退出码、输出与对应代码状态。
- 阅读差异，解释关键逻辑，以及失败时 `out` 为何符合约定。
- 说清哪些结论来自工具结果，哪些仍只是解释或推测。

## 5. 验收条件

| 项目 | 完成条件 |
| --- | --- |
| 任务定义 | 本人能明确目标、约定、允许范围及完成条件 |
| 上下文 | 本人能解释选材依据，识别约定与实现的差异 |
| 系统行为 | 接口签名不变，起始测试及补充测试通过，修改符合全部约定 |
| 有效测试 | 原用例保留；新增测试针对未覆盖要求，失败时检查输出保持原值 |
| 修改检查 | 差异只涉及允许文件，构建产物留在被忽略的 work 中 |
| 代码解释 | 本人能解释关键判断、数值处理与失败状态，允许查阅和使用 AI |
| 迁移或故障 | 完成下面一个小变式或基于实际故障组织定位，保留证据 |

有限测试通过仍不等于覆盖所有字符串。验收时还需要从接口约定独立检查遗漏，并写明局限。本人解释和迁移尚未验证时，个人掌握保持未验收。

## 6. 小变式与故障任务（修复后再做）

选择其一，不在本页预填实现或答案：

- **小变式**：派生一个局部副本，新增“输入最多 5 个字符”的业务限制，其余约定不变。先指出原约定中哪一部分被替换，再更新相应用例；主实验继续保留原约定。副本放本实验 `work/variant/`，不得借变式更改主实验头文件。
- **故障排查**：根据本人或 AI 首次修复中真实出现的失败，先提出可检查的原因，构造区分这些原因的输入，再修复并重跑；若没有真实失败，可在 `work/fault/` 副本中主动引入一个单点错误，要求自己补测识别。不把阅读现成解释当作排错完成。

## 7. 记录与恢复

个人记录放本地计划，原始输出可放被忽略的 `work/`：任务文本、上下文选择、运行前判断、实际命令与结果、差异、本人解释、变式或故障表现、所需帮助。系统结果与个人状态分栏记录。

如需重做，先保存自己的修改，再建立一个新的局部副本；不直接用覆盖命令抹掉旧成果。本材料准备阶段保留缺陷起点，不交付参考修复，不填写个人复盘。

真实项目任务若已覆盖上述能力，可直接在原仓库完成并引用证据，无需重复本实验。测试源码与项目实现始终留在原仓库。
